# Рішення, припущення, ризики

## Рішення

| ID | Рішення | Причина / наслідок |
| --- | --- | --- |
| ADR-01 | Від першого етапу єдиний 3D-світ | Пряме уточнення користувача: звичайний Chrome показує 3D-гру |
| ADR-02 | Chrome → VR → онлайн | Прямий порядок користувача, кожен етап має gate |
| ADR-03 | Спільне headless core з Vector3 | Одні правила для бота, людини та сервера |
| ADR-04 | Перша особа; desktop mouse-look, VR tracked view | Прямий перехід до занурення; власний розмір потребує хороших візуальних сигналів |
| ADR-05 | TypeScript + Three.js; без окремого фізичного рушія | Прості сферичні взаємодії визначені формулами |
| ADR-06 | Сервер авторитетний, WebSocket | Клієнт не визначає масу/перемогу; додаються затримки й reconciliation |
| ADR-07 | Спільні онлайн-кімнати Chrome/Quest | Та сама геометрія, швидкість і нормалізований ввід; рівність UX перевіряється |
| ADR-08 | Поділ/віруси/викидання відкладені | Зберегти чіткий обсяг базового циклу; це робоче припущення |
| ADR-09 | Без акаунтів і постійного рейтингу у v1 | Мінімальна операційна складність; результат лише за матч |
| ADR-10 | Повні snapshots 10 Hz на старті | Простіше відновлення; збільшений трафік вимірюється |
| ADR-11 | Немає teleport та server rewind | Однакова геометрія руху; високий RTT може погіршити відчуття поглинань |

ADR-04–11 — запропоновані проєктні рішення. Їх можна переглянути за плейтестом/вимірами до відповідного gate. Це не підстава мовчки змінювати визначену користувачем 3D-гру на плоску арену.

## Реєстр ризиків

| Ризик | Перевірка/сигнал | Дія |
| --- | --- | --- |
| Дискомфорт від вільного 3D-руху | T-209, часті завершення тесту | Налаштувати ввід/віньєтку/темп; повторити плейтест |
| Власний великий радіус незрозумілий із центра | Користувачі не розуміють поглинання | Контур тіла, підказки відносного розміру, індикатор контакту |
| Складно знаходити їжу у 3D | Довгі інтервали без цілей | Підібрати щільність, контраст і сигнали відстані |
| Quest перегрівається/втрачає кадри | T-208 після прогріву | Instancing, зменшення overdraw/деталізації, повторний вимір |
| Desktop/VR мають різну керованість | Порівняльний плейтест зі зміною пристроїв | Налаштувати ввід; за потреби окремі черги як майбутнє рішення |
| Ріст створює безвихідну перевагу | Розподіл результатів/мас | Змінити cap, exponent швидкості, густину їжі через rulesVersion |
| Snapshot трафік завеликий | Byte budget/slow sockets | Спершу вимір; потім окрема версія delta протоколу |
| Різні runtime дають похибки | Replay та reconciliation | Серверний пріоритет, не вимагати міжплатформного lockstep |
| XR API або браузер змінився | Реальний Quest smoke перед релізом | Feature detection і зрозумілий fallback |
| Немає фізичного Quest для QA | T-201–210 BLOCKED | Не позначати VR завершеним; отримати апаратний звіт |
| Падіння процесу завершує матчі | Restart тест | Автоперезапуск, повідомлення, документована відсутність recovery |

## Що уточнюється під час реалізації

- Точний ноутбук для приймання — до performance gate S1.
- Колірна схема, остаточна назва й звуки — перед завершенням M4.
- Числовий баланс — за плейтестом M5; зміни документувати.
- Доступ до фізичного Quest 2 — до gate S2.
- Хостинг, регіон, бюджет і публічний домен — до M12.
- Комфортна швидкість й HUD — після перевірки на шоломі.

Ці питання не блокують ядро, 3D-геометрію та desktop-прототип за початковими параметрами.

## Технічні джерела

Перевірено 2026-09-20. Нижче — джерела API, не джерела наших правил балансу.

- [Three.js WebXRManager](https://threejs.org/docs/pages/WebXRManager.html): XR-камера, сесія, reference space, контролери.
- [MDN: requestSession](https://developer.mozilla.org/en-US/docs/Web/API/XRSystem/requestSession): immersive-vr, secure context, дія користувача та відмови.
- [Meta: WebXR overview](https://developers.meta.com/horizon/documentation/web/webxr-overview/): браузерні immersive-сесії.
- [Meta: browser specifications](https://developers.meta.com/horizon/documentation/web/browser-specs/): runtime feature detection та тестування на шоломі.
- [Meta: WebXR frame rate](https://developers.meta.com/horizon/documentation/web/webxr-frames/): робота з частотою кадрів; доступність перевіряти в runtime.

Документація постачальника може змінитися. Перед реалізацією відповідного API перевірити актуальні сигнатури та сумісність обраних версій. Наша ціль 72 Hz є критерієм проєкту, а не твердженням про частоту за замовчуванням.
