# Етап 3 — онлайн для Chrome та VR

## Обсяг і кімнати

Один авторитетний серверний процес Node.js на старті. WebSocket через WSS. Спільна 3D-арена та rulesVersion для обох типів клієнтів.
Кімната — до 8 людей, ціль 8 активних учасників загалом; порожні людські місця доповнюються ботами. При приході людини прибрати одного бота наприкінці tick без нагороди чи перенесення маси. Якщо місце зарезервовано за disconnected гравцем, воно не заповнюється ботом до закінчення резерву.
У локальній грі лишаються 1 людина + 8 ботів; різна кількість учасників є конфігурацією режиму.

Кімната створюється з коротким випадковим кодом і living lobby. Кожен гравець натискає Ready. Коли є хоча б одна людина і всі connected люди готові — 3 s countdown. Творець не отримує влади над симуляцією; його вихід не закриває кімнату.
Під час матчу нові гравці можуть приєднуватися з масою 20 і стандартним захистом. Матч закінчується через 18000 tick незалежно від виходів.
Після результату через 15 s — lobby, готовність усіх скидається. Порожня кімната видаляється через 60 s після зникнення останньої людини та reconnect-резерву. Після перезапуску процесу активні матчі не відновлюються.

## Смерть та відсутність вводу

Людський actor залишається у кімнаті після смерті. Кнопка «Відродитися» активується через 3 s, нова клітина має новий entityId, масу 20 і захист 3 s. Статистика actor накопичується за матч. Автоматичного відродження немає.
У підсумковій таблиці жива клітина має поточну масу, мертвий actor — 0; далі cellsEaten, потім actor ID. PeakMass показується окремо.
Меню/втрата Pointer Lock/XR надсилає нульовий ввід. Світ продовжується, клітина залишається вразливою; показати це перед входом в онлайн.
Якщо остання валідна команда старіша за 250 ms — сервер обнуляє рух. Відключена клітина лишається у світі, може бути поглинута, не телепортується і не стає невразливою.

## Протокол v1

JSON UTF-8, discriminated union за type. Кожне повідомлення містить protocolVersion=1. Числа скінченні; ID/коди/рядки з обмеженнями. Розміри вказані для декодованих байтів UTF-8.

| Напрям / type | Поля та зміст |
| --- | --- |
| C→S hello | buildId, rulesVersion, platform(desktop|vr); сервер перевіряє сумісність |
| C→S createRoom | requestId, displayName |
| C→S joinRoom | requestId, roomCode, displayName |
| C→S ready | requestId, ready:boolean |
| C→S input | seq, direction:{x,y,z} |
| C→S respawn | requestId |
| C→S resume | requestId, resumeToken |
| C→S leave | requestId |
| C→S ping | nonce |
| S→C welcome | playerId, roomCode, resumeToken, rulesVersion, config, serverTick, phase |
| S→C snapshot | serverTick, phase, remainingTicks, lastProcessedSeq, entities, actors, leaderboard |
| S→C event | eventId, serverTick, eventType, actorId, entityId, payload |
| S→C result | matchId, reason, standings, stats |
| S→C ack | requestId, status |
| S→C error | requestId?, code, retryable, message |
| S→C pong | nonce, serverTick |

Input приклад:
```json
{"protocolVersion":1,"type":"input","seq":42,"direction":{"x":0.6,"y":0.0,"z":0.8}}
```

Snapshot містить повний стан: для клітин id, actorId, position, mass, protectedUntilTick; для їжі id та position; для actor — стан alive/dead/disconnected і статистику. Radius виводиться з mass.
lastProcessedSeq стосується адресата snapshot. eventId унікальний у матчі; ефект обробляється один раз. Джерело відновлення стану — snapshot, тому пропущена анімаційна подія не змінює правила.
requestId — унікальний на клієнті; сервер кешує до 128 відповідей/гравця на 60 s, повтор create/join/respawn не виконує дію вдруге.
seq — зростаюче ціле 0..2^31-1 у межах з'єднання; сервер відкидає <= останнього прийнятого. При resume seq починається з 0 у новому з'єднанні, старе закривається. Останній валідний напрямок застосовується на наступних tick до заміни/тайм-ауту; не обробляти пакет як додатковий крок симуляції.

Коди: ROOM_NOT_FOUND, ROOM_FULL, VERSION_MISMATCH, INVALID_MESSAGE, RATE_LIMITED, RECONNECT_EXPIRED, SESSION_REPLACED, SERVER_OVERLOAD, SERVER_RESTART.
Невалідний handshake не запускає гравця. protocolVersion/rulesVersion повинні збігатися; buildId дозволяє різні сумісні клієнтські збірки.

## Частоти та синхронізація

Сервер — 60 tick/s. Клієнт надсилає напрямок 30 разів/s, включно з нульовим. Snapshot — 10 разів/s. Перший варіант надсилає повні snapshots, без delta та interest management; це простіше перевірити й відновити.
Клієнт показує віддалені сутності з буфером 150 ms; адаптація 100–250 ms залежно від jitter. Якщо буфер спорожнів, екстраполяція за двома останніми позиціями максимум 100 ms, потім зупинка і знак нестабільної мережі. Не екстраполювати через смерть або спавн.
Локально передбачається тільки рух за останнім відомим mass; їжа/маса/смерть підтверджуються сервером. При snapshot зіставити передбачену позицію на serverTick, виправити базу й повторно застосувати збережені локальні команди після цієї часової точки.
lastProcessedSeq допомагає прибрати підтверджені команди; це не кількість tick виконання напрямку. Історія містить estimatedServerTick і утримуваний напрямок. Через мережевий час replay приблизний, серверна позиція завжди має пріоритет. Історія обмежена 2 s.

Малі похибки desktop згладжуються за 100 ms. У VR не коригувати tracked pose: зміщення rig до 0.25 одиниці згладити за 150 ms; більше — коротка віньєтка і виправлення rig. Якщо такі виправлення часті, мережевий VR не проходить приймання.
Для поглинання немає rewind/lag compensation; сервер перевіряє поточний стан. Це відомий компроміс першого релізу, що потребує тесту на 100 ms RTT.

## Перепідключення

Сервер генерує непрогнозований resumeToken щонайменше 128 біт, зберігає лише digest; токен не є roomCode. Передавати тільки WSS, не URL, не журнали.
Після розриву резервувати actor до 15 s. Клієнт повторює з'єднання через 0.5, 1, 2, 4 s із jitter, потім кожні 4 s до завершення вікна. Після успіху токен ротувати, видати повний snapshot, відкинути старе передбачення. Actor міг загинути під час відсутності.
Після завершення вікна — меню і нове приєднання без старої маси. У браузері токен лише в пам'яті поточної сторінки; перезавантаження не гарантує resume.

## Безпека й ресурси

- Сервер приймає намір руху, ніколи position/mass/score/dt клієнта.
- direction довший за 1 нормалізується; NaN, Infinity, відсутні/невідомі поля та невідомий type відхиляються схемою.
- C→S максимум 4 KiB/повідомлення; input до 60/s, burst 15. Інші повідомлення до 10/s, burst 10. Повторне порушення протягом 10 s закриває socket.
- Створення кімнат: максимум 5/min/IP, до 2 активних кімнат на IP на старті; ліміти конфігуровані для спільних NAT.
- Перевіряти Origin за allowlist. TLS на ingress; websocket compression вимкнено у v1. Контент імен показувати як текст.
- Ім'я 1–20 Unicode code points після trim; прибрати керівні символи. Без чатів і довільного HTML.
- roomCode із криптографічного RNG, 8 символів із 32-символьного алфавіту. Це засіб запрошення, не обліковий запис; join-спроби лімітуються.
- Черга виходу socket >1 MiB: пропускати застарілі snapshots; якщо стан не покращується 5 s, закрити slow consumer, не блокувати кімнату.
- Secrets лише в env сервера. Не логувати токени, сирі пакети чи XR-пози голови. Технічні журнали зберігати 7 днів; IP для rate limit в оперативній пам'яті.

## Мережеві бюджети

Цілі: median RTT <=100 ms для тестового регіону, p95 <=150 ms; стабільна гра при 100 ms RTT, jitter ±20 ms і 1% втрат TCP-трафіку. Окремий сценарій деградації — 200 ms RTT/3% втрат. WebSocket на TCP, тому втрати тестуються на транспорті як затримка повторної доставки, а не перестановка JSON у сокеті.
Максимальний snapshot 256 KiB; ціль egress <=1.5 MiB/s на клієнта за 800 їжі/8 клітин. Це верхній бюджет, фактичний трафік виміряти; для слабкого каналу може знадобитись delta encoding як наступна версія.
Початкове приймання сервера: 10 кімнат × 8 клієнтів на зафіксованому Linux 4 vCPU/8 GiB. Це тестова ціль, не обіцянка місткості будь-якого хостингу.

## Узгоджений wire-контракт реалізації v0.1

Цей розділ уточнює початковий ескіз повідомлень вище. Канонічні TypeScript-типи та runtime-перевірки: packages/protocol/index.ts.

- welcome: protocolVersion, playerId, roomCode, resumeToken, rulesVersion.
- snapshot: protocolVersion, state, phase кімнати, countdown у секундах, roster, lastProcessedSeq, foodMode, removedFood.
- state: tick, config, phase симуляції, reason, humanId, actors, cells, food.
- foodMode=replace: state.food є повним набором; клієнт очищає попередній.
- foodMode=patch: state.food містить лише додані елементи, removedFood — видалені ID.
- На новій сесії, перепідключенні та новому матчі обов'язковий replace. TCP зберігає порядок патчів; після розриву стару історію не використовувати.
- Стан клітин і акторів завжди повний; клієнт не підтверджує собі масу/поглинання.
- ack: requestId, status. error: requestId за наявності, code, message. pong: nonce.
- Окремі event/result не передаються: завершення визначається phase/reason та авторитетною статистикою.
- lastProcessedSeq оновлюється після виконання tick. Кеш requestId належить гравцеві та зберігається у межах reconnect-резерву.

Межа snapshot 256 KiB залишається. Початковий бюджет egress є верхньою межею; повна повторна передача нерухомої їжі більше не використовується.
